# OSC 7447 — a terminal escape sequence for structured prompt metadata

**Status:** experimental, single implementation. Not registered with anyone,
because there is nobody to register with.

**Version:** the `chips` message described here is v1. See
[Compatibility](#compatibility) — there is no version field, by design.

---

## What this is

A private [OSC](#background-what-is-an-osc) escape sequence that lets a shell
hand structured metadata to whatever is reading its output — a terminal
emulator, a multiplexer, or an editor hosting a PTY — instead of only painting
that metadata as characters the reader has to scrape back out.

The motivating case: a shell prompt already computes the current git branch,
virtualenv, language version, and cloud profile on every prompt. It renders
them as decorated text. Anything downstream that wants those same values has
two bad options — re-derive them (duplicating logic, paying for another `git
status` on every prompt, risking a blocked UI) or parse them back out of styled
terminal output (fragile, and impossible once the prompt is drawn with images).
OSC 7447 lets the shell say what it already knows.

It is deliberately narrow. It is not a general RPC channel, not a
serialization format, and not a replacement for [OSC
133](#relationship-to-osc-133) shell integration — it is a companion to it.

## Background: what is an OSC?

An Operating System Command is an ANSI/ECMA-48 escape sequence for
out-of-band communication with the terminal:

```
ESC ]  <code> ; <payload>  ST
```

`ST` (String Terminator) is `ESC \`. A bare `BEL` (`0x07`) is also widely
accepted as a terminator for historical reasons; readers of this protocol
MUST accept both.

The `<code>` selects the command. In practice:

| Code | Purpose | Origin |
|------|---------|--------|
| `0`, `2` | set window/icon title | xterm, universal |
| `7` | report working directory | de facto |
| `8` | hyperlinks | de facto |
| `52` | clipboard access | xterm |
| `99` | desktop notifications | kitty |
| `133` | shell integration / semantic prompt marks | FinalTerm; adopted broadly |
| `633` | shell-integration extensions | VS Code, private |
| `1337` | inline images, file transfer | iTerm2, private |

**There is no registry.** Low numbers are settled by convention; high numbers
are unclaimed space that implementations squat on. The property that makes
this workable is the parsing rule every conforming terminal follows: an OSC
with an unrecognized code is consumed up to its terminator and **discarded
silently**. Emitting a private OSC into a terminal that has never heard of it
is therefore inert — not an error, not stray text on screen.

## Why 7447

Nothing technical. 47 is the running numeric in-joke of *Star Trek*'s
TNG-and-later writers' rooms, and this protocol was built for an LCARS-styled
terminal environment. 7447 is a palindrome of it, which suits a grammar built
from symmetric key/value pairs.

Practically, it needed to be a number nobody else uses. `133` is the standard
being extended; `1337` collides with iTerm2; `633` collides with VS Code. 7447
has no assignment known to this author in any terminal emulator.

## Format

```
ESC ] 7447 ; lcars ; <message> [ ; <field> ]... ST
```

- **`7447`** — the OSC code.
- **`lcars`** — a fixed namespace token. Present so that if another
  implementation ever squats 7447, the two are trivially distinguishable and
  each can ignore the other's traffic rather than misparse it. A reader MUST
  ignore any OSC 7447 whose first field is not a namespace it owns.
- **`<message>`** — the message type. A reader MUST ignore message types it
  does not recognize.
- **`<field>`...** — message-specific, `;`-separated.

### Escaping

`;` separates fields, so within any field value:

| Byte | Encoded as |
|------|-----------|
| `%`  | `%25` |
| `;`  | `%3B` |

`%` must be encoded first when emitting, and decoded last when parsing.

Encoding only these two is a deliberate choice: it keeps payloads
human-readable in a trace (`git;main` stays `git;main`), which matters more
for a debugging-adjacent protocol than uniformity would. A general
percent-decoder on the reading side is harmless and is what the reference
implementation uses.

Field values MUST NOT contain `ESC`, `BEL`, or C0 control bytes; a reader
encountering them SHOULD discard the whole message. Values are UTF-8.

### Length

Readers SHOULD impose a maximum OSC length and discard sequences that exceed
it, to bound memory when a stream is corrupt or hostile. The reference
implementation caps at 4096 bytes.

## The `chips` message

A "chip" is one labelled fact about the shell's current state — the kind of
thing a decorated prompt shows as a coloured segment.

```
ESC ] 7447 ; lcars ; chips [ ; <kind> ; <label> ]... ST
```

Fields after `chips` are **flat alternating pairs**. There is no nesting.

```
ESC]7447;lcars;chips;venv;lcarcat;git;main;gitstate;02-STAGED ESC\
```

An empty chip set is the bare form, with no trailing `;`:

```
ESC]7447;lcars;chips ESC\
```

This MUST still be emitted and MUST still be delivered to the application —
it is how a reader learns to clear a previously-shown set. Silence means "no
new information", not "nothing to show".

A trailing `<kind>` with no `<label>` is a truncated message; the reader MUST
drop that pair and keep the rest.

### Kinds

The emitter names what a chip **means**. It does not name a colour, a width,
or a position. Presentation belongs entirely to the reader, which is what lets
one shell drive several very different displays.

| Kind | Meaning |
|------|---------|
| `git` | current branch, tag, or `detached` |
| `gitstate` | one working-tree state count, e.g. `02-STAGED` |
| `venv` | active virtualenv name |
| `py` | language/runtime version in effect |
| `aws` | active cloud profile |
| `awsdep` | as `aws`, but flagged as a production/dangerous profile |

A reader MUST render an unrecognized kind rather than dropping it, using a
default presentation. Forward compatibility depends on this: it is how an
emitter can add a kind without waiting for every reader to be updated.

Multiple chips MAY share a kind (`gitstate` typically repeats). Order is the
emitter's suggested display order, left to right.

### What does not belong in `chips`

Anything scoped to a *command* rather than to the *shell state at prompt time*.

The reference implementation learned this the hard way with exit status. A
shell's `precmd` hook runs after a command completes, so `$?` there describes
the command that just finished — but the chips it emits attach to the prompt
about to be drawn, i.e. the *next* command's context. Emitting an `err` chip
put the failure on the wrong entity. Exit status is a property of a finished
command; OSC 133's `D;<code>` already reports it, correctly scoped.

If a fact answers "what just happened", it is not a chip.

## Relationship to OSC 133

OSC 7447 assumes OSC 133 and adds to it. 133 marks *when* things happen; 7447
says *what the environment is*.

A typical prompt emits, in order:

```
ESC]133;D;0 ESC\                          previous command finished, exit 0
ESC]133;A ESC\                            prompt begins
ESC]7447;lcars;chips;git;main ESC\        environment for the coming command
ESC]7;file://host/path ESC\               working directory
ESC]133;B ESC\                            prompt ends, input begins
```

Chips are emitted **after `133;A`**, so a reader that creates per-command state
at `A` has somewhere to put them. Emitting before `A` is legal but means the
reader may have nowhere to attach the data.

## Compatibility

There is **no version field**, deliberately. Versioning is carried by the
message-type token instead:

- Unknown **message type** → ignored. A future `chips2` with a different
  grammar is invisible to old readers rather than misparsed.
- Unknown **kind** → rendered with default presentation. New facts reach old
  readers degraded, not dropped.
- Extra trailing fields on a known message → ignored.

The failure this avoids is a version number that readers check and then reject
on, which turns every emitter update into a hard cutover. The cost is that a
breaking grammar change requires a new message name.

This does mean a *newer reader* cannot detect an *older emitter*; it sees
absence, which is indistinguishable from a shell that does not implement the
protocol at all. That is the intended reading in both cases: show nothing.

## Security

- Payloads are **untrusted input**. A chip label can contain anything a branch
  name can contain, and branch names come from remotes. Readers MUST treat
  labels as data — never as a path, command, format string, or markup.
- Readers MUST bound OSC length (above).
- Emitters SHOULD NOT put secrets in chips. This data crosses every pipe the
  terminal output crosses, including logs, `script` captures, and screen
  recordings. A cloud *profile name* is appropriate; a token is not.

## Open questions

Unresolved, and the reason this is marked experimental:

1. **Is `lcars` the right namespace token to standardize on?** It names one
   project. A shared token with per-implementation sub-namespacing might serve
   a published protocol better.
2. **Should `chips` be the only message?** Prompt metadata is one use; the
   envelope would carry others.
3. **Is squatting 7447 acceptable long-term**, or should this live as a private
   sub-command inside OSC 133 — extending a standard nobody owns versus using a
   number nobody owns?
4. **Kind vocabulary.** The current set is what one prompt happened to compute.
   A published version would want a defined core set plus a convention for
   implementation-specific kinds (a `x-` prefix, say).
